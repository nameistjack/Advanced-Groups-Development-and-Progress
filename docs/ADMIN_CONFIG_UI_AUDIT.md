# Admin Config Studio UI Audit

This document tracks visual, usability, accessibility, and security findings from in-game screenshots of the Admin Config Studio. It is an implementation backlog and should be extended as additional screens are reviewed.

Broader architectural lessons and non-UI improvements are tracked in `ENGINEERING_REFERENCE_AUDIT.md`.

## Goals

- Make configuration controls readable against every game scene.
- Prevent clipping and overlap across supported resolutions and safe-zone scales.
- Give editable controls, status information, warnings, and actions a clear hierarchy.
- Protect secrets displayed in configuration fields.
- Keep all sections visually consistent.

## Priority 0: Security

### Mask webhook credentials

Webhook fields currently display complete URLs, including credentials. Treat any URL captured in a shared screenshot as compromised and regenerate it at the provider.

Required changes:

- Mask webhook URLs by default.
- Show only a short non-sensitive prefix and suffix.
- Add an explicit press-and-hold or temporary reveal action.
- Never include complete webhook URLs in logs, summaries, notifications, or screenshots generated by the UI.
- Add a `Test webhook` action that does not require revealing the value.

Acceptance criteria:

- Opening the Permissions page never exposes a complete webhook credential.
- Copying or revealing a credential requires an intentional action.
- Validation errors identify the affected field without echoing its value.

## Priority 1: Layout and readability

### Define responsive screen sizing and scaling

The studio needs one documented sizing system. At present it reads `GetScreenSize()` only when the page is shown, caps the panel at `1760 × 1000`, uses mostly fixed-width columns, and switches the summary off at a single width threshold. It also forces the body to be at least 760 pixels high, which can exceed the available panel height on short displays.

Required sizing flow:

1. Read the current workspace width and height.
2. Derive a safe usable rectangle from configurable edge margins.
3. Select a wide, medium, or compact layout from both width and height—not width alone.
4. Size and center the outer window within that usable rectangle.
5. Reserve scaled header and footer heights.
6. Give the remaining height to a scrollable body; never force the body taller than the window.
7. Allocate body width proportionally between navigation, active content, and optional status.
8. Clamp interactive controls to minimum usable sizes.
9. Recalculate when the page opens and whenever resolution, window size, or UI scale changes.

Do not solve smaller screens by shrinking all text and controls indefinitely. Reflow or collapse secondary regions first.

Suggested outer-window policy:

```text
usableWidth  = screenWidth  - (2 × safeMarginX)
usableHeight = screenHeight - (2 × safeMarginY)

windowWidth  = clamp(usableWidth  × 0.88, compactMinimumWidth, 1760)
windowHeight = clamp(usableHeight × 0.92, compactMinimumHeight, 1000)
```

The minimum must never override the available usable size. If the screen is below the preferred minimum, use the compact layout and consume the usable rectangle instead.

Choose one scaling owner:

- Use proportional layout geometry plus DayZ `scaled` text/control behavior, or
- Apply an explicit UI scale to exact-pixel measurements.

Do not apply both inconsistently. Exact values should be reserved for minimum hit targets, icons, borders, and row heights; major regions should use proportions and clamps.

Recommended breakpoints:

| Mode | Entry condition | Structure |
|---|---|---|
| Wide | usable width ≥ 1500 and usable height ≥ 800 | Navigation + active content + persistent status |
| Medium | usable width 1100–1499 or limited height | Narrow navigation + active content; status becomes a toggleable drawer |
| Compact | usable width < 1100 or usable height < 700 | Section selector above content; status becomes a separate view; fixed footer remains visible |

Breakpoint values should be validated in-game and centralized as constants rather than repeated across page controllers.

Acceptance criteria:

- Opening at 16:9, 16:10, 21:9, 32:9, and compact window sizes produces an intentional composition.
- Changing resolution or UI scale does not require closing and reopening the menu.
- No body region extends beneath the footer or outside the safe usable rectangle.
- Text size and button hit areas stay usable in compact mode.
- Ultrawide screens gain breathing room but do not stretch forms into excessively long rows.

### Allocate space proportionally

The screenshots show a large gap between logical groups while the actual form controls are compressed. Each layout mode needs an explicit space budget.

Recommended wide-mode body proportions, after gaps:

- Navigation: 16–18%
- Active content: 56–62%
- Status/summary: 20–24%

Recommended medium-mode proportions:

- Navigation: 18–22%, with a minimum usable label width
- Active content: remaining width
- Status: hidden behind a visible toggle/drawer, not silently discarded

Recommended compact-mode proportions:

- Section selector: full width, compact horizontal tabs or dropdown
- Active content: full remaining width
- Status/summary: separate full-width view or overlay drawer

Within forms:

- Label column: approximately 32–38%
- Control column: approximately 62–68%
- Boolean rows may use a fixed checkbox followed by a flexible label.
- List/detail editors should start near 34/66 and permit context-specific adjustment.
- Logs should use the complete active-content width rather than preserve an empty form column.
- Headers and footers should have bounded scaled heights; the body absorbs remaining space.

Space should follow task importance. Primary editable content receives the largest share; navigation stays scannable; status remains available without competing with the form.

### Centralize responsive layout behavior

Create one layout-metrics/controller layer responsible for:

- Screen and usable-rectangle measurement
- Safe margins
- Current breakpoint
- UI scale and minimum hit target
- Header, footer, gaps, and row metrics
- Column proportions
- Popup clamping and preferred placement
- Resolution/UI-scale change detection

Individual sections should request metrics or populate responsive containers rather than manually repositioning dozens of named widgets. This prevents each page from developing a different scaling model.

### Add a cohesive window and component system

The studio currently appears as independent controls floating over the world. Bright terrain, roads, player clothing, and shadows reduce readability. This does not require a heavy or nearly opaque full-screen overlay: a clean DayZ-native result can be achieved with a contained window, consistent row surfaces, and controlled local contrast.

Required changes:

- Place the studio inside a clearly bounded, centered or draggable window.
- Use a restrained translucent background for the window and stronger local surfaces behind rows, headers, inputs, and footers.
- Use reusable row components for booleans, text, integers, selections, colors, notes, and section headings.
- Generate long forms inside a vertical scroll host instead of manually positioning every field in one large layout.
- Use separate surfaces for section navigation, active settings, and preview/status only where that grouping improves comprehension.
- Keep the player model and world scene from showing through form controls.
- Preserve a consistent outer margin from the safe-zone edges.

Suggested construction pattern:

- Window shell with a title bar and contained content host
- Scroll widget containing a size-to-content vertical spacer
- Reusable 32–40 pixel row layouts with consistent label and control columns
- Dedicated compact layouts for boolean, text, number, selection, color, note, and action rows
- Fixed footer owned by the window rather than positioned against the screen
- Optional draggable, pinnable, or resizable behavior without sacrificing safe-zone bounds

### DayZ UI techniques required by this implementation

The current AdvancedGroups layouts, in-game screenshots, and DayZ widget behavior show that the interface can remain clean and efficient without a heavy full-screen overlay. The implementation should use these project-owned techniques consistently:

- Define shared widget styles for normal, hover, pressed, focused, and disabled states instead of coloring each widget independently.
- Provide semantic variants such as primary, ghost, and destructive buttons.
- Give edit boxes and checkboxes purpose-built styles with unmistakable focus and disabled states.
- Use nine-slice panel and control textures where rounded or bordered surfaces must scale cleanly.
- Use a proportional outer window with exact-pixel headers, icons, rows, and minimum control sizes.
- Keep the window draggable and bounded, with a compact icon/title/subtitle header and an obvious close action.
- Use localized string keys for headings, labels, notifications, and tooltips.
- Populate repeatable content into `GridSpacerWidget` or `WrapSpacerWidget` hosts with size-to-content enabled.
- Use compact list entries that expose edit/delete actions on the row instead of rendering every record as a full form.
- Separate list selection from detail editing for collections such as webhook profiles, roles, markers, and event rules.
- Disable Save until a valid selection or draft exists, and confirm destructive or high-impact operations.
- Use collapsible section headers whose hidden content reflows through an `Ignore invisible` parent spacer.
- Centralize tooltip, confirmation-dialog, dropdown, and edit-box behavior in reusable controller helpers.

These techniques reduce layout duplication, make interaction states consistent, and allow the interface to remain legible over the game world with moderate translucency.

### Fix clipping and overflow

Observed clipping includes checkbox labels, webhook values, log lines, helper text, and the Apply/Reset buttons.

Required changes:

- Give the active settings column more width.
- Use scroll containers for long forms and log content.
- Wrap explanatory text; clip or horizontally scroll machine-oriented log lines.
- Ensure every label has enough width at supported UI scales.
- Test ultrawide, 16:9, and narrower safe-zone configurations.

Acceptance criteria:

- No label, value, heading, or action is cut off at the tested resolutions.
- The content column scrolls without moving the header or footer.
- The player model cannot visually cover controls.

### Create a fixed action footer

Apply and Reset currently float over the game/player and are partially clipped.

Required changes:

- Place actions in a fixed footer inside the studio panel.
- Right-align the primary Apply action.
- Style Reset as a neutral or warning secondary action.
- Disable Apply when there are no unsaved changes.
- Keep actions visible while the active form scrolls.

Suggested layout:

```text
[Reset changes]                              [Apply changes]
```

## Priority 1: Information hierarchy

### Improve section navigation

- Use dark inactive buttons instead of pale gray bars.
- Mark the selected section with a strong fill or accent rail.
- Increase internal padding and maintain consistent row heights.
- Add scrolling if the section list grows.
- Keep selected, hover, focused, and disabled states visually distinct.

### Rebuild Preview / Summary

The right column mixes red, orange, and cyan text at small sizes without clear grouping. Red is currently used for ordinary state, weakening its meaning as an error color.

Split it into compact cards:

- Save status
- Reload status
- Validation issues
- Effective rule summary
- UI preview

Use light neutral text for normal state, cyan for selection/information, yellow for warnings, and red only for errors or destructive state.

### Clarify top toolbar actions

The three colored icon buttons do not communicate their purpose clearly.

- Add tooltips and accessible labels.
- Use consistent icon sizes and button frames.
- Show disabled state when an action is unavailable.
- Consider text labels if the icons are not universally recognizable.

## Priority 2: Forms and controls

### Make editable values look editable

General-limit values currently resemble plain text.

- Give edit boxes a dark fill, border, focus state, and consistent width.
- Validate numeric fields and show permitted ranges.
- Add units such as seconds and days where relevant.
- Consider increment/decrement controls for small bounded values.
- Align labels and fields to a consistent grid.

### Improve Permissions / Integrations

The page is too dense when every event shows a full webhook URL.

- Move webhook configuration into a dedicated subsection or collapsible card.
- Present a default webhook first.
- Let each event select `Use default` or `Custom override`.
- Hide override inputs until enabled.
- Add per-field validation state and a test action.
- Keep Global PVE and friendly-fire controls in their own gameplay-protection group.

### Improve Chat / Moderation

Observed issues:

- Checkbox text competes with nearby input labels.
- The bad-word input is visually detached from its enable checkbox.
- The vicinity range value does not clearly look editable.
- Role-tag instructions describe one-entry-per-line input, but the visible controls resemble separate single-line fields.
- Steam ID, tag, and color controls lack strong grouping and validation feedback.
- The color value appears incomplete or ambiguous, and the RGB controls are too small to interpret comfortably.

Required changes:

- Group chat toggles, filtering, mute behavior, range, and role tags into separate cards.
- Disable and dim the bad-word field when filtering is off.
- Pair each checkbox with its dependent control.
- Use a proper multiline role-tag editor or a repeatable row list with Add/Delete actions.
- Validate Steam IDs as 17-digit identifiers.
- Validate colors as exactly six hexadecimal digits and normalize display consistently.
- Replace tiny RGB boxes with labeled sliders or numeric fields plus a larger color swatch.
- Show row-level validation messages without relying on color alone.

## Priority 2: Admin Log

The log is difficult to read and clips horizontally.

Required changes:

- Add an opaque log surface and vertical scrollbar.
- Add level filters: All, Info, Warning, Error.
- Add search, copy, clear-view, and refresh actions.
- Color only the level indicator instead of the complete line.
- Use a monospaced font where available.
- Preserve complete lines through wrapping, horizontal scrolling, or a detail view.

## Visual system

Adopt a consistent semantic palette:

- Primary text: white or light gray
- Secondary text: muted gray
- Selection and focus: cyan
- Warning: yellow or amber
- Error/destructive: red
- Success/applied: green

Define consistent type roles for page title, section title, field label, input text, helper text, and validation message. Avoid using small red text for ordinary labels.

## Suggested implementation order

1. Rotate exposed webhook credentials and mask secret fields.
2. Implement centralized screen metrics, safe margins, breakpoints, and space proportions.
3. Build the reusable window shell, row components, scroll host, and fixed footer.
4. Fix clipping, scrolling, live resize handling, and player-model overlap.
5. Normalize typography, colors, navigation states, and edit-box styling.
6. Rebuild Permissions webhook controls.
7. Rebuild Chat role-tag and color controls.
8. Upgrade Admin Log filtering and navigation.
9. Run a resolution and UI-scale screenshot pass across every section.
